전체 구조

요청 처리 흐름

POST /api/chat 한 번이 처리되는 순서입니다 (routers/chat.py).

  1. 대화 · 사용자 메모리 불러오기저장된 대화에서 직전 턴의 routed_agent · routed_skill과 각 답변의 trace(tool 호출 · 결과)를 찾아 붙인다.
  2. 후보 계산 — 코드사용자가 고른 tool · skill을 모두 쓸 수 있는 agent만 후보로. 사용자가 skill을 고르지 않았으면 필수 tool을 후보 agent가 쓸 수 있는 skill만 후보로.
  3. Router — LLM 1회 (ROUTER_MODEL, 기본 gpt-4o-mini)agent와 skill을 같이 고른다. 응답 스키마가 후보 id의 enum이라 후보 밖 값은 나올 수 없다. 직전 턴의 agent · skill은 유지하는 쪽으로 기울인다(sticky). 후보가 하나뿐이고 skill 후보도 없으면 호출하지 않는다.
  4. 최종 tool 계산 — 코드 (plan_tools)(사용자 선택 또는 skill tool 또는 agent 기본 group) ∪ skill 필수 tool − 끈 tool ∩ agent 허용 범위 ∩ 지금 응답하는 MCP tool. 빠진 tool은 이유와 함께 화면 · 프롬프트에 알린다.
  5. 프롬프트 조립공통 원칙 + agent 프롬프트 + 켜진 tool의 안내만(tool_guides.yaml) + skill 절차(SKILL.md 본문) + 사용자 메모리 + 사용 불가 tool 경고.
  6. ReAct 실행 (LangGraph)켜진 tool만 bind_tools. tool 조합별로 그래프를 컴파일해 LRU 캐시. 이전 턴 trace는 tool 메시지로 다시 넣는다.
  7. 저장답변 · tool 요약 · trace · 라우팅 결과를 대화에 저장, skill 사용 횟수 증가, 사용자 메모리는 백그라운드로 갱신.

판단은 두 곳에 나눠 둔다. 수치 기준이 정해진 판단(예: PM 전후 defect 30% 이상 감소면 효과 있음)은 판단 tool 코드에 둬서 매번 같은 결과가 나오고 검증 가능하게 한다. 순서 · 분기 · 해석 · 보고 형식은 SKILL.md 본문에 둔다.

Skill

폴더 하나가 skill 하나입니다. 화면(스킬 메뉴)에서 만들거나 고쳐도, 에디터로 직접 고쳐도 같은 파일이 바뀝니다. 폴더를 넣으면 생기고 빼면 사라집니다 (재시작 불필요).

backend/skills/sk_morning/SKILL.md
---
name: sk_morning              # = 폴더명(id)
title: 출근 전 라인 점검        # 화면 표시명
description: 전일 이슈 + 현재 WIP + Open Hold 를 한 번에 정리   # Router 판단 근거
tools:                        # 이 workflow의 필수 tool (MCP tool 이름)
- get_daily_report
- get_wip_status
- get_lot_hold_info
---

1. 전일 이슈 리포트로 P1~P2 항목을 먼저 확인한다.
2. P1 이 장비 DOWN 이면 해당 Area 의 현재 WIP 를 조회해 대기 WIP 를 함께 보고한다.
...

Skill이 적용되는 방식

skill_mode언제예
manual사용자가 화면에서 skill을 골랐을 때스킬 메뉴 → 실행
router질문이 skill의 업무를 해 달라는 요청일 때 Router가 고름"M14 CMP 출근 전 라인 점검 해줘" → sk_morning
sticky직전 턴의 skill 절차 진행 중, 사용자가 되물음에 답하거나 "계속"할 때 유지"3번 wafer로 계속해줘" → sk_defect 유지
none단발 조회 · 일반 질문 · 주제 전환"TE2FE35 wafer map 보여줘", "dishing이 뭐야?"

Skill이 적용되면 그 skill의 필수 tool만 켜진다. LLM이 보는 tool 수 자체가 줄어 선택 정확도가 오른다. AUTO_SKILL=0이면 자동 선택을 끄고 사용자가 고른 skill만 쓴다.

맥락 유지 (trace)

프론트는 대화 텍스트만 보냅니다. 텍스트만 넘기면 "아까 조회한 것 중 OOC 슬롯만" 같은 후속 질문에서 LLM이 앞서 조회한 원본 데이터를 보지 못해 다시 조회하거나 값을 지어냅니다. 그래서:

  • 턴이 끝나면 그 턴의 tool 호출과 결과를 대화 기록에 trace로 저장 (결과는 tool당 3000자까지).
  • 다음 턴에 최근 3턴의 trace를 실제 tool 메시지(AIMessage.tool_calls + ToolMessage)로 다시 넣는다.
  • trace는 서버 내부용 — 화면으로 내려가는 대화 조회 API에서는 뺀다.

확장 방법

조회 · 판단 tool 추가 (ceeria)

  • siria/core/xxx_service.py에 순수 로직
  • siria/tools/xxx_tools.py에 @tool @safe_tool wrapper + register()
  • docstring에 무엇을 / 언제 / 다른 tool과 구분 — LLM의 선택 기준
  • MCP 서버는 수정 불필요 (registry 전체 노출)
  • 허브 catalog.yaml의 group에 이름 추가

Skill(업무 workflow) 추가

  • 화면 스킬 메뉴에서 만들기, 또는 backend/skills/<id>/SKILL.md 직접 작성
  • description은 "언제 쓰는지"를 분명히 — Router가 이걸 보고 고른다
  • tools에는 절차에 필요한 tool 전부
  • 본문: 단발 질문이면 해당 tool만 쓰고 끝낸다는 규칙 + 단계별 절차 + 보고 형식

차트가 있는 tool

  • tool_guides.yaml에 차트 태그 형식 추가
  • 필요하면 화면용 ui_* tool을 MCP에 추가하고 catalog.yaml ui_tools에 등록
  • 프론트 차트 컴포넌트 + 태그 파싱 추가

agent 추가

프롬프트(업무 방식)가 달라야 할 때만. 단순히 tool 조합이나 절차가 다르면 skill이나 group으로 해결한다.

실행 (로컬)

# 1) fab MCP — :8100
cd fab_mcp && ../backend/venv/bin/python -m server

# 2) ceeria MCP — :8200
cd siria && ../backend/venv/bin/python -m adapters.mcp_server --http

# 3) Coris 허브 — :8000
cd backend && ./venv/bin/uvicorn main:app --reload

# 4) 프론트 — :3000 (/api 는 8000 으로 프록시)
cd frontend && npm start

MCP 서버가 늦게 뜨거나 죽어도 허브는 기동합니다. 응답하지 않는 서버의 tool은 "사용 불가"로 표시되고 MCP_REFRESH_SEC(기본 60초)마다 다시 받아옵니다.

판단 tool 작성예정

조회 tool 위에 수치 기준 판정 로직을 MCP tool로. 조회/판단 구분 표시는 이때 함께 정한다.

skill별 실행 설정검토

단계가 많은 workflow는 recursion_limit(현재 16 고정)이 부족할 수 있다. SKILL.md frontmatter로 지정하는 방안.

모델 · 엔드포인트 환경변수화예정

회사 LLM(vLLM 등)에 맞춰 허브 · ceeria 설정을 통일.

평가셋예정

질문 → 기대 agent · skill · tool. 프롬프트 · catalog · skill 변경 시 회귀 확인.

siria 실행부 정리검토

ceeria의 tool은 MCP로 이관 완료. 자체 agent factory · FastAPI · MCRS SKILL.md를 계속 둘지 결정.

차트를 tool 결과로 렌더검토

지금은 LLM이 차트 태그를 써야 그려진다. tool 결과에 render 정보를 담아 프론트가 직접 그리면 누락이 없다.
